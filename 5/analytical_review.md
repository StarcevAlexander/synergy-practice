# Кейс-задача № 5 — Аналитический обзор проделанной работы

**Объект анализа:** WEB-приложение «Турагентство» из кейс-задачи № 4
(трёхзвенная WEB-архитектура: браузер → сервер приложений Flask → БД).

Ниже работа оценена по критериям из индивидуального задания, после чего
предложены способы решения выявленных проблем.

---

## 1. Функциональность
Приложение корректно решает поставленные задачи: отображает каталог туров,
карточку конкретного тура, принимает заявки клиентов и выводит их списком.
Все основные пользовательские сценарии (просмотр → заявка → проверка заявки)
работают и проверены вручную. Входные данные формы валидируются на уровне
HTML (`required`, `type=number`, `min=1`). Реализованы аналитические запросы
к БД (стоимость заказа, выручка по направлениям).
**Оценка: высокая.** Базовый функционал покрыт полностью.

## 2. Производительность
Запросы простые, выполняются за миллисекунды; на справочных таблицах
объёмом до тысяч строк задержек не возникает. Узким местом при росте нагрузки
станет работа SQLite в режиме одиночного файла и отсутствие пула соединений.
Для текущего учебного объёма данных производительность избыточно достаточна.

## 3. Удобство использования (юзабилити)
Интерфейс минималистичный, адаптивный (`viewport`, проценты ширины),
с понятной навигацией «Каталог / Заявки» и читаемой типографикой.
Сообщения об ошибках пока скудные: при ошибке ввода пользователь видит
стандартную страницу 404/500 без подсказки. Это снижает дружелюбность интерфейса.

## 4. Безопасность
Параметризованные запросы (`?`-плейсхолдеры) защищают от SQL-инъекций.
Однако отсутствует CSRF-защита форм, экранирование пользовательского ввода
полагается только на автоэкранирование Jinja2, нет HTTPS и аутентификации.
Для продакшена это критично, для учебного стенда — приемлемо.

## 5. Масштабируемость
Архитектура трёхзвенная, поэтому слой данных можно вынести на MS SQL Server
(схема приложена) и масштабировать сервер приложений горизонтально за балансировщиком.
Код разделён на роуты и шаблоны, что упрощает добавление новых сущностей.
Ограничение — SQLite не рассчитан на параллельную запись.

## 6. Сопровождаемость
Код структурирован: доступ к БД, роуты и представление разделены, есть
docstring и комментарии, шаблоны наследуются от `base.html`. Это упрощает
внесение изменений. Не хватает миграций схемы и автоматических тестов API.

## 7. Переносимость
Приложение кроссплатформенно: Python + Flask работают на Windows/Linux/macOS.
БД абстрагирована — для локального запуска используется SQLite, для целевой
среды задания приложена схема MS SQL Server. Перенос требует лишь смены драйвера БД.

## 8. Качество кода
Код читаемый, придерживается PEP 8, использует осмысленные имена и типовые
аннотации. Применён паттерн «приложение-фабрика данных» через `get_db()`/`teardown`.
Магические значения вынесены минимально; бизнес-логика тонкая. Дублирование отсутствует.

## 9. Тестирование
Для задач № 1 и № 2 написаны автотесты (`test_task1.py`, `test_task2.py`),
проверяющие граничные случаи. WEB-приложение протестировано вручную;
автоматических тестов роутов пока нет — это основной пробел в покрытии.

---

## Выявленные проблемы и способы их решения

| Проблема | Способ решения |
|----------|----------------|
| Нет автотестов роутов | Добавить тесты на `app.test_client()` (pytest + Flask) |
| Слабая обработка ошибок в UI | Добавить страницы-обработчики 404/500 и flash-сообщения |
| Отсутствие CSRF-защиты | Подключить Flask-WTF, добавить CSRF-токены в формы |
| Нет аутентификации | Ввести вход для менеджера (Flask-Login) перед доступом к заявкам |
| SQLite ограничивает запись | Перейти на MS SQL Server (схема готова) + пул соединений |
| Нет миграций схемы | Использовать Alembic/Flask-Migrate для версионирования БД |
| Нет HTTPS | Развернуть за reverse-proxy (nginx/IIS) с TLS-сертификатом |

## Вывод
Приложение полностью выполняет функциональные требования и пригодно как учебный
прототип. Наибольший потенциал улучшения — в области безопасности и тестирования;
перечисленные меры переводят прототип в состояние, близкое к промышленному.
